# The sweep

The requirements nobody writes down. Walk **every** row and say where it landed.

Three answers are complete:

- a check id — `RF-104 → C7`
- **already covered** — name the existing constraint, and read it to confirm it is actually there
- **not in scope because X** — a reason, not a shrug

Anything else is silence. A generic answer is silence with a word in front of it: *"authorization:
handled"* names nothing, binds nothing and proves nothing.

**Each row binds through the repository**, never through this file. The `ef-harness` block in the
repo's context file and the Stage 3 contract say what the category means here. Where a row has no
binding in this repo, say so — that is a finding, not an omission.

**A row whose input is empty costs a line, not a pass.** A feature with no new surface owes no
authorization row. Say "no new surface" and move on; working through an empty category is how a small
feature pays a large feature's tax.

---

## 1. Identifier exposure

Which identifier may cross the boundary, and **everywhere** the rule applies — responses, event
payloads, audit records, log lines, error messages.
*Binds via:* `identifier:`.
*Why it is missed:* the rule is usually enforced on responses and forgotten on the other four.

## 2. Input validation at the surface

Every new or changed surface has its validation actually attached — not merely written.
*Binds via:* the repo's validation mechanism, named in the contract.
*Why it is missed:* a schema that exists but is not wired reads identical to one that is.

## 3. Authorization gate

Every new surface passes the repo's policy mechanism, with the right resource and action. Where the
spec says a guarantee holds everywhere, there is **no direct read of the underlying flag** that
bypasses it.
*Binds via:* `authorization:`.
*Why it is missed:* one bypass makes a cross-cutting guarantee false, and the bypass is usually older
than the feature.

## 4. Transaction and atomicity boundary

What is atomic with what. No write escaping the transaction through a non-transactional handle. No
side effect emitted inside a transaction that can roll back. Where the contract requires one atomic
step, there is not a read-then-write.
*Binds via:* the contract's transaction boundary section.

## 5. Idempotency and retry

What happens when the same request, message or delivery arrives twice. What is safe to retry, and
what the retry budget is.
*Why it is missed:* the happy path is written first and the second delivery never tested.

## 6. Concurrency and ordering

Two actors doing this at once. Whether order matters and what enforces it. Any "only one at a time"
claim, and what actually makes it true.

## 7. Failure modes and the error contract

Every failure a caller must distinguish, and how they distinguish it. No signal that means two
things — a field populated on both the success and failure path, or a status that does not
discriminate what the caller must act on.
*Why it is missed:* errors are added where they are thrown, not where they are consumed.

## 8. External dependency failure

What happens when the thing you depend on is down, slow, or returns garbage. Whether the fallback is
distinguishable from a legitimate empty result — a silent fallback turns a failure into a confident
wrong answer.

## 9. Data lifecycle

What is retained, for how long, what deletes it, and what a backfill does to existing rows. Whether
an "optional" field being absent means *leave it* or *clear it* — the destructive default is the
most expensive single bug this sweep catches.

## 10. State transitions

The states this introduces, every legal transition into and out of them, and what rejects an illegal
one. An enumeration that grew needs every exhaustive switch over it extended.

## 11. Generated code and schema provenance

Generated artifacts regenerated by their real command, with the tree clean afterwards. Schema changes
created the way the repo requires, never hand-written.
*Binds via:* `generated:` and `migrations:`.
*Why it is missed:* it passes locally because the generated file is already there.

## 12. Audit trail and observability

Side effects that must leave a record, and where that record is catalogued. Log lines and metrics a
human needs to diagnose this in production — and the identifier rule applies to all of them.
*Binds via:* `audit:`.

## 13. Public interface documentation

The repo's API description artifact regenerated or updated for every changed surface. A consumer
reading stale docs builds against a contract that no longer exists.

---

## Writing the result

Sweep rows go into the checklist under `## Swept`, one line each, in this order. They are read back
by Stage 5: a row that resolves to **already covered** is checked against the code, and a cited
constraint that turns out not to be there is a finding.
